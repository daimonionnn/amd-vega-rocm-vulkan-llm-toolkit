# AMD's prebuilt ROCm 7.14 for gfx900 on this APU — builds, does not run

> **Superseded in part, same day.** ROCm 7.14 *does* run on this APU — just not
> from AMD's wheels. A different 7.14 build of the same source
> (`mixa3607/rocm-gfx906:7.14-complete`) enumerates the GPU fine, and combined
> with the gfx900 kernels out of AMD's wheel it runs llama.cpp correctly. See
> [2026-09-11-rocm714-working.md](2026-09-11-rocm714-working.md). Everything
> below about AMD's wheel build still holds; the conclusion that "the backport
> stays because 7.14 cannot work here" does not.

Tested 2026-09-11 against `rocm-sdk-*-7.14.0a20260612` from
<https://rocm.nightlies.amd.com/v2/gfx900/>, on Ryzen 5700G / Vega 8 (gfx90c),
Ubuntu 26.04, kernel 7.0.

## What works

The SDK is real and complete for gfx900, not a stub:

- `rocm-sdk targets` reports `gfx900`
- `_rocm_sdk_libraries_gfx900/lib/rocblas/library/gfx900/` holds **182 Tensile
  files**, a superset of the 128 this repo backports from ROCm 6.3.4
- llama.cpp **configures and compiles cleanly** against it for `gfx900`, with
  `patches/0001` applied, producing a working `libggml-hip.so` with no
  unresolved dependencies

## What does not

The runtime segfaults during GPU enumeration, before llama.cpp is involved:

```
$ rocminfo
Segmentation fault (core dumped)          exit=139

$ python3 -c 'ctypes.CDLL("libamdhip64.so.7").hipGetDeviceCount(...)'
core dumped

$ rocm-sdk test
Ran 26 tests — 25 passed, 1 error:
  CalledProcessError: '/usr/local/bin/rocminfo' died with SIGSEGV
```

`llama-bench` therefore fell back to CPU (87.10 t/s on gemma, matching this
machine's known CPU prefill) until `LD_LIBRARY_PATH` was set, after which it
segfaulted too.

**It is not the override.** `rocminfo` segfaults identically with
`HSA_OVERRIDE_GFX_VERSION=9.0.0` and with it unset. So this is the ROCm 7.14
userspace failing on this host, not the gfx90c→gfx900 substitution.

## Where it crashes, precisely

Backtrace from the real ELF (`_rocm_sdk_core/bin/rocminfo`; `/usr/local/bin/rocminfo`
is a pip console-script wrapper and gdb cannot load it):

```
#0  0x0000000100000001 in ?? ()
#1  rocr::AMD::GpuAgent::InitDma()      from libhsa-runtime64.so.1
#2  rocr::AMD::GpuAgent::PostToolsInit()
#3  rocr::core::Runtime::Load()
#4  rocr::core::Runtime::Acquire()
#5  rocr::HSA::hsa_init()
#6  main
rip 0x100000001
```

So it dies inside **`hsa_init()`**, in SDMA/blit setup — before any agent is handed to
the caller, which is why nothing that looks like enumeration ever prints. `rip` is
`0x100000001`, not `0x0`: an indirect call through a **garbage function pointer**, not a
null dereference.

### Two hypotheses tested and rejected

**Not an unknown architecture.** The obvious guess was that ROCr 7.14 has no gfx90c in
its target table and mishandles the unknown chip. It does have it — `strings` finds
`gfx90c` in the 7.14 runtime. (Curiously, the *working* 7.2 runtime contains none of
`gfx900`/`gfx90c`/`gfx906` as strings at all; it derives target names numerically.)

**Not the SDMA knobs.** Given `InitDma`, and given this repo has run
`HSA_ENABLE_SDMA=0` since April because SDMA is unstable on this APU, the env route was
worth trying. None of these avoids the crash:

| Setting | Result |
| --- | --- |
| `HSA_ENABLE_SDMA=0` (the repo default) | SIGSEGV |
| `HSA_ENABLE_SDMA=1` | SIGSEGV |
| `HSA_ENABLE_PEER_SDMA=0` | SIGSEGV |
| `HSA_ENABLE_SDMA_GANG=0` | SIGSEGV |
| `HSA_ENABLE_SDMA_RECOMMENDED_ENG=0` | SIGSEGV |
| `HSA_DISCOVER_COPY_AGENTS=0` | SIGSEGV |

The last three are variables that exist in 7.14 and **not** in the working 7.2 runtime,
so this code path was rewritten between the two versions.

### What the crash actually is: destroying a corrupt `std::function`

Disassembly at the crash site, with registers:

```
InitDma+1532:  test %rax,%rax        ; null check on the pointer
InitDma+1535:  je   +1550            ; skip the call if it is null
InitDma+1537:  mov  %rsp,%rdi        ; arg1 = &stack object
InitDma+1540:  mov  %rdi,%rsi        ; arg2 = same object
InitDma+1543:  mov  $0x3,%edx        ; arg3 = 3
               call *%rax            ; rax = 0x100000001  -> SIGSEGV

rax 0x100000001   rdi 0x7fffffffe760   rsi 0x7fffffffe760   rdx 0x3   rbp 0x0
```

Two things follow.

**The pointer is not null, it is garbage.** The `test`/`je` pair immediately before is an
explicit null check, and it passed. So this is not a missing initialisation that a null
guard would catch; something wrote a nonsense value.

**The call is `std::function`'s manager.** libstdc++ invokes
`_M_manager(_Any_data& dest, const _Any_data& source, _Manager_operation op)`, and its
operation enum is `__get_type_info=0, __get_functor_ptr=1, __clone_functor=2,
__destroy_functor=3`. Here `rdi == rsi` (the same stack object as both dest and source)
and `edx = 3` — this is **`__destroy_functor`**, the destructor path of a local
`std::function`.

So: `InitDma` destroys a `std::function` whose `_M_manager` pointer is `0x100000001`.
That value is `(1 << 32) | 1` — two adjacent 32-bit fields both holding 1, read as one
64-bit pointer. It looks exactly like a structure being read at the wrong offset, which
points at an ABI or layout mismatch rather than at ordinary logic error.

This is consistent with the new code in `InitDma`, which wraps the queue lambdas in
further lambdas and passes them to `lazy_ptr::reset()` — creating temporary
`std::function` objects that 7.2.0 never created.

### The source is public, and InitDma did change

The library embeds its build path: `/__w/TheRock/TheRock/rocm-systems/projects/
rocr-runtime/runtime/hsa-runtime/core/runtime/amd_gpu_agent.cpp`. So it is built from
the [ROCm/rocm-systems](https://github.com/ROCm/rocm-systems) monorepo, **not** the
standalone [ROCm/ROCR-Runtime](https://github.com/ROCm/ROCR-Runtime) repo — which matters,
because in ROCR-Runtime `InitDma` is byte-identical between `rocm-7.2.0` and
`amd-staging`, and diffing there produces nothing.

Against `projects/rocr-runtime/.../amd_gpu_agent.cpp` in rocm-systems it does differ:

- Internal blit queues now call **`queue->SetProfiling(true)` immediately after
  creation**, wrapped in new lambdas, where 7.2.0 simply stored `queue_lambda`
- `CreateInterceptibleQueue()` gained an argument
- The queue-priority enum changed type
- **`isa_` was replaced by `supported_isas()[0]`** throughout, including in
  `CreateBlitSdma`

The **`SetProfiling(true)` wrapper lambdas** are now the prime suspect rather than
`supported_isas()`: they are precisely the temporary `std::function` objects the
disassembly shows being destroyed, and they do not exist in 7.2.0 at all.

**That remains a suspicion, not a finding.** No debug symbols are published for these
wheels (`rocm-sdk-core-dbg` and `-debug` both 404), so confirming it means building ROCr
with symbols from `ROCm/rocm-systems` — with the caveat that a build from current
`develop` may not reproduce a June 2026 binary's bug at all.

### Two wrong turns, recorded so they are not repeated

**"The runtime does not know gfx90c."** Rejected: `strings` finds `gfx90c` in the 7.14
runtime. (The working 7.2 runtime contains none of `gfx900`/`gfx90c`/`gfx906` as strings
at all — it derives target names numerically, which is why grepping for them proves
nothing on its own.)

**"`BlitSdmaV4` was removed."** A first read of the ROCR-Runtime diff showed
`- sdma = new BlitSdmaV4();` and looked conclusive, since SDMA v4 is what GFX9 hardware
uses. It was a misread: the removal is in the `case 11/12` DXG branch. `case 9` — this
GPU — still constructs `BlitSdmaV4` in every version checked.

### What the kernel offers it

KFD describes the device completely and sanely, so this is not missing topology:

```
gfx_target_version 90012      (= gfx90c)     simd_count 32
num_sdma_engines 1            num_sdma_xgmi_engines 0
num_sdma_queues_per_engine 2  sdma_fw_version 40
num_xcc 1                     device_id 5688 (0x1638)
```

`num_sdma_engines 1` with `num_sdma_xgmi_engines 0` is the sort of minimal configuration
a rewritten multi-engine selection path might not handle, and `sdma_fw_version 40` is low
by modern standards — but both are speculation. **The root cause inside `InitDma` is not
established**; determining it needs ROCr debug symbols or its source, neither of which
was pursued here.

## Reading

This is the same wall as June 2026, when modular `amdrocm-core` 7.13/7.14
rejected the override with `HSA_STATUS_ERROR_OUT_OF_RESOURCES` — a newer ROCr
that does not work on this APU. It is now a segfault rather than a clean error,
which is worse behaviour but the same conclusion.

**Scope:** this says nothing about *discrete* gfx900. A Vega 56/64 or MI25 is
native gfx900 on a dGPU path and may well work; issue #1 reports a V340 running
ROCm 7.14 packages successfully. The failure here is specific to this APU.

**Consequence:** the Tensile backport into classic ROCm 7.2 stays. It is not
obsolete, and the "replace it with AMD's prebuilt SDK" idea is closed for this
machine.

## Two traps worth keeping

1. **The SDK is three wheels, the cmake config assumes one tree.**
   `hip-lang-config.cmake` execs `<root>/bin/amdllvm`, but `rocm-sdk path
   --root` points at `_rocm_sdk_devel`, which has no `bin/`; the toolchain is in
   `_rocm_sdk_core/lib/llvm/bin`. The reported error is the misleading
   `clangrt builtins lib could not be found`. `build/Dockerfile.rocm714-sdk-vega`
   symlinks around it.

2. **The HIP backend failing to load is silent.** With `GGML_BACKEND_DL=ON`,
   `libggml-hip.so` is dlopened at run time; if its dependencies are not on
   `LD_LIBRARY_PATH`, llama-bench prints `backend: CPU` and produces a plausible
   number. Always check the backend column.
