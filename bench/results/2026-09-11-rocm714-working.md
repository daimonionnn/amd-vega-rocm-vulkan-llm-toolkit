# ROCm 7.14 does work on this APU — just not AMD's wheel build

2026-09-11. This reverses the conclusion recorded earlier the same day in
[2026-09-11-rocm714-sdk-gfx900.md](2026-09-11-rocm714-sdk-gfx900.md), which
found AMD's gfx900 wheels segfaulting in `hsa_init()` and concluded the
backport into classic ROCm 7.2 had to stay.

## The decisive comparison

| ROCm 7.14 build | `rocminfo` on this gfx90c APU |
| --- | --- |
| AMD pip wheels, `rocm-sdk-* 7.14.0a20260612` | **SIGSEGV** in `GpuAgent::InitDma()` |
| `mixa3607/rocm-gfx906:7.14-complete` | **exit 0**, reports `gfx900:xnack-` |

Same ROCm version, same build system (TheRock), different builder and
configuration. So the crash is **not a property of the ROCm 7.14 source**; it is
specific to AMD's wheel build. That is worth knowing before anyone spends a
night compiling ROCr to chase a source bug that is not there.

## Putting a working 7.14 together

mixa3607's image is built for gfx906 and ships only `rocblas/library/gfx906/`.
AMD's unusable wheel ships a complete `rocblas/library/gfx900/` — 182 Tensile
files, built for 7.14. Both use the same per-architecture layout, so the
directory drops straight in:

- working ROCr and HIP runtime from mixa3607
- gfx900 kernels from AMD's wheel
- `patches/0001` applied as everywhere else

[`build/Dockerfile.rocm714-mixa-gfx900`](../../build/Dockerfile.rocm714-mixa-gfx900)
does this as a two-stage build, so nothing is vendored into this repo.

**Note this is not the ROCm 6.3.4 backport used elsewhere here** — these are
AMD's own 7.14-built kernels. 7.14's rocBLAS also lays its library out per
architecture (`library/gfx900/`) where 6.3.4 and 7.2 use one flat directory.

Whether the 6.3.4 files themselves work on 7.14 was **never tested here**. An
earlier version of this page stated that they are the wrong format and abort at
the first GEMM; that was an assumption, not a measurement, and
[issue #1](https://github.com/daimonionnn/amd-vega-rocm-vulkan-llm-toolkit/issues/1) reports the
opposite — those files running under AMD's modular rocBLAS 7.14.1 on a discrete
Vega 10, with correctness-verified SGEMM.

## It computes correctly

`test-backend-ops test -o FLASH_ATTN_EXT -b ROCm0`: **2959/2959 passed**, the
same as on ROCm 7.2. This matters more than the timings below: a silent
fallback or a miscompiled kernel can produce a plausible number, and this repo
has been caught by that three separate ways.

## Performance against ROCm 7.2 + the 6.3.4 backport

Both builds carry `patches/0001`. `llama-bench -ngl 99 -fa 1 -b 4096 -ub 4096`.

| Model | Metric | ROCm 7.2 | ROCm 7.14 | Δ |
| --- | --- | ---: | ---: | ---: |
| gemma | prefill @4K | 247.22 | 245.97 | −0.5 % |
| gemma | prefill @16K | 202.13 | 199.56 | −1.3 % |
| 35B | prefill @4K | 151.94 | 149.32 | −1.7 % |
| 35B | decode @16K | 17.45 | 17.13 | −1.8 % |
| **gemma** | **decode @16K** | **13.64 ± 0.63** | **12.43 ± 0.51** | **−8.9 %** |

Three of four cells match within measurement noise. The gemma decode cell does
not: measured back to back at `-r 2` on the same thermal state, 7.14 is about
9 % slower, and a separate `-r 1` run gave 12.08 in the same direction. With
standard deviations around 0.5–0.6 the gap is roughly two sigma — suggestive
rather than conclusive, and worth a proper repeat before it is treated as fact.

It is notable that the only divergence is decode on the dense model, which is
the case that leans hardest on flash attention at depth.

## Full matrix, and what the regression actually is

12 cells, both builds measured back to back in each cell so neither gets a
thermal advantage. `-fa 1`, `-b 4096 -ub 4096`, `-r 1`. Raw data:
[`2026-09-11-rocm714-vs-72-matrix.tsv`](2026-09-11-rocm714-vs-72-matrix.tsv).

| Model | Metric | 4K | 16K | 32K |
| --- | --- | ---: | ---: | ---: |
| gemma | prefill | −0.9 % | −0.9 % | −0.8 % |
| **gemma** | **decode** | **−9.3 %** | **−8.7 %** | **−7.6 %** |
| 35B | prefill | +1.9 % | +0.4 % | +1.3 % |
| 35B | decode | −0.9 % | −2.8 % | −0.8 % |

Eleven of twelve cells are within noise. The regression is confined entirely to
**gemma decode**, and it is consistent across every context.

### It is not `patches/0001`

The obvious suspect was the patch, since it is inline assembly — the one thing
whose code generation depends most on compiler version, and gemma's head dim of
512 selects a different flash-attention specialisation than the 35B's 256. So:
measure with `-fa 0`, where flash attention and the patch are not used at all.

| gemma decode @16K, `-r 2` | ROCm 7.2 | ROCm 7.14 | Δ |
| --- | ---: | ---: | ---: |
| `-fa 1` | 13.62 | 12.43 | −8.7 % |
| `-fa 0` | 9.29 | 8.56 | **−7.9 %** |

**The gap survives.** The patch is not involved, and neither is flash attention.

### What it probably is

Decode at batch 1 does not go through rocBLAS — it runs llama.cpp's own GEMV
kernels (`mmvf`/`mmvq`). Both builds compile that same source with different
compilers: ROCm 7.2's LLVM on the host, mixa3607's in the container. A dense
model and an MoE take different kernels there — MoE goes through `mul_mat_id` —
which fits gemma losing ~8 % while the 35B does not.

That makes compiler code generation on the dense decode path the working
explanation. It is consistent with every cell, but it has not been confirmed by
inspecting the generated code, so it stays a hypothesis.

## What this changes

**The backport is not obsolete, but it is no longer the only option.** ROCm 7.2
plus the 6.3.4 Tensile files remains the tested default and is currently
slightly faster. A 7.14 path now exists, is verified correct, and would be the
place to start if a newer ROCm becomes necessary.

**The bug report needs rewriting.** It is no longer "ROCm 7.14 crashes on
gfx90c" but "AMD's 7.14 gfx900 wheel build crashes where another 7.14 build of
the same source does not" — narrower, more actionable, and pointing at
packaging rather than at ROCr's logic.
